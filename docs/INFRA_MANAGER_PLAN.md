# 팀장 인프라 수행 기능 — 설계 문서

## Context

사용자가 도메인 하나를 알려주면 ai-crew가 알아서 DNS/SSL/배포 같은 인프라 설정을 처리해주는 기능을 원했다. 논의 과정에서 세 가지 형태를 검토했고, 최종적으로 **별도 역할을 새로 만들지 않고 팀장 자체에 인프라 수행 능력을 추가**하는 쪽으로 정리했다. 이 문서는 그 결론에 이르기까지 기각한 대안과, 채택한 설계의 구체적인 내용을 정리한다.

---

## 검토했던 대안과 기각 사유

### 1. 직원(티켓 기반 백그라운드 실행)

ai-crew의 기본 패턴 — 팀장이 티켓을 만들어 위임하면 직원이 백그라운드에서 알아서 끝내고 완료 시 자동으로 보고한다.

**기각 사유**: 인프라 작업은 사용자가 진행 상황을 실시간으로 지켜보다가 필요하면 즉시 개입하고 싶어했다. 직원은 작업 중 사람이 끼어들 방법이 "수정 요청"(작업이 끝나거나 막힌 뒤 세션을 이어서 지시)뿐이라 동기적인 실시간 개입이 안 된다.

### 2. 팀장 옆의 별도 "인프라 담당" (팀별 다른 팀장)

팀장처럼 사용자와 실시간 채팅하되, 인프라 전용 성격/툴을 가진 두 번째 역할을 만드는 안.

**기각 사유**: 지금 ai-crew는 팀장 프롬프트(`agents/manager.md`)가 모든 팀에 공유되는 단일 파일이라, 팀마다 다른 성격의 팀장을 두는 기능 자체가 없다. 이걸 만들려면 팀별 팀장 프롬프트/툴셋을 지원하는 아키텍처 확장이 필요한데, 복잡도 대비 얻는 이득이 크지 않다고 판단했다.

### 3. (채택) 팀장 자체가 인프라 작업을 직접 수행

팀장은 이미 사용자와 실시간으로 대화하는 유일한 존재다. 별도 역할을 만들지 않고, 팀장에게 브라우저 자동화 툴을 쥐여주고 "인프라 작업은 예외적으로 직접 해도 된다"는 규칙만 추가하면 목표를 달성할 수 있다.

---

## 설계

### 1. 브라우저 자동화 — Playwright + 영속 프로필

**Claude in Chrome을 쓰지 않는 이유**:
- Claude Code 헤드리스(`claude -p`) 세션이 이 확장 프로그램의 MCP 서버에 붙을 수 있는지 확인되지 않았다 — 이 확장은 인터랙티브 세션 전용으로 보인다.
- 붙는다 해도 사용자의 **실제 로그인된 메인 크롬**을 그대로 쓰게 되어, 인프라 계정뿐 아니라 그 브라우저에 로그인된 다른 모든 계정까지 접근 가능한 상태로 자동화가 돈다 — 위험 범위가 불필요하게 넓다.

**대신 Playwright를 MCP 서버로 감싸 팀장에게 툴로 제공한다.**

로그인을 매번 새로 하지 않아도 되도록, 사용자가 미리 로그인해둔 세션을 그대로 이어 쓴다:

- `launchPersistentContext(userDataDir, ...)`로 **인프라 자동화 전용 프로필 폴더**를 지정해서 브라우저를 띄운다. 이 폴더는 진짜 크롬 프로필처럼 쿠키/로그인 세션을 디스크에 저장하므로, 사용자가 그 프로필로 도메인 등록업체·클라우드 콘솔 등에 한 번만 로그인해두면 다음부터 팀장이 그 프로필로 브라우저를 열 때마다 로그인된 상태로 시작한다.
- 더 가벼운 대안으로 `storageState`(쿠키/토큰 스냅샷)를 파일로 저장해뒀다가 매번 복원하는 방법도 있다.
- **이 프로필은 사용자의 평소 메인 크롬 프로필과 분리한다.** 인프라 자동화에 필요한 사이트만 로그인해두는 전용 프로필을 따로 만들어, 위험 범위를 그 프로필에 로그인된 사이트로만 한정한다.

### 2. 팀장 프롬프트 확장

- `agents/manager.md`가 모든 팀에 공유되는 단일 파일이므로, 이 기능을 켜면 **모든 팀의 팀장**이 인프라 작업을 할 수 있게 된다. 특정 팀에만 한정하려면 별도의 팀별 분기가 필요하며, 이번 설계 범위 밖이다.
- 기존 규칙("팀장은 직접 코드를 수정하지 않는다, 위임하고 확인만 한다")에 **인프라 작업에 한해 예외**를 명시적으로 추가한다. 코드 작업은 여전히 위임 전용으로 남는다 — 이 예외는 인프라 카테고리에만 적용된다.
- 팀장의 MCP 설정(`buildClaudeMcpConfig`, `runner/src/manager/invoke.ts`)에 Playwright MCP 서버를 추가로 연결한다.

### 3. 필수 안전장치 — 매 설정 변경 전 사용자 확인

사용자가 명시적으로 요구한 사항이다: *"설정을 하기 전에 꼭 물어봐야 해, 실수할 수도 있으니."*

- DNS 등록, SSL 발급, 배포 설정 변경 등 **실제로 상태를 바꾸는 액션을 실행하기 직전에는 예외 없이 확인 절차를 거친다.** 자동 승인은 허용하지 않는다.
- 기존 ai-crew의 `requireApproval`/`needs_approval` 패턴과 철학은 같지만, 이번엔 팀장 스스로 위험도를 판단해서 선별하는 게 아니라 **"인프라 상태를 바꾸는 액션" 카테고리 자체를 항상 확인 필요로 취급**한다. 조회성 동작(DNS 레코드 확인, 현재 설정 조회 등)은 확인 없이 진행해도 된다.
- 구체적인 확인 메커니즘은 기존 `ask_user` MCP 툴을 그대로 쓰거나, 조금 더 명시적인 "실행 직전 최종 확인" 단계를 추가하는 방안 중 선택이 필요하다 (아래 열린 질문 참고).

### 4. 실행 모델 변화

팀장은 원래 "사용자 메시지가 오면 짧게 응답하고 끝나는 job" 패턴이다(`invokeManager`, 매 호출마다 새 프로세스, 응답 후 종료). 인프라 작업은 여러 단계의 브라우저 조작 + 중간 확인을 거치므로 한 턴이 상당히 길어질 수 있다. 문제가 되는 건 아니지만, 지금까지의 "빠르게 응답하고 빠지는" 팀장 호출 패턴과는 성격이 다르다는 점을 인지하고 있어야 한다.

## 열린 질문 / 다음 단계

- 팀별로 이 기능을 켜고 끌 수 있게 할지, 아니면 전역으로 둘지.
- Playwright MCP 서버를 직접 구현할지, 기존에 나와 있는 오픈소스 Playwright MCP 서버를 가져다 쓸지.
- 영속 프로필을 호스트의 어느 경로에 둘지, 여러 팀이 같은 프로필을 공유해도 괜찮은지(동시에 두 팀장이 같은 프로필로 브라우저를 띄우면 충돌 가능성).
- "실행 직전 확인"을 `ask_user` 그대로 쓸지, 별도 UI(예: 액션 미리보기 + 승인 버튼)를 새로 만들지.
